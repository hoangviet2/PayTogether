# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

The web app is a first-time flow backed by `Backend/`. After Log in with PayPal the user lands on a home dashboard (their spent / pending / bills to accept across trips; all zero for a new user), then creates a trip (just me or with a group) or joins one with its code. A user tells Wayfinder (OpenAI) where to go in the chat, and the group walks the `AI/ai.md` phases (Destinations → Timeline → Places → Pricing → Booked → On trip → Settled). The mobile app still runs on the sample trip in `FrontEnd/shared/trip.ts`. Product rules and invariants live in `claudee.md` and `AI/ai.md`. The stack is not the Next.js/Postgres one `claudee.md` describes: it is Vite + a small node:http server with a JSON file store.

## Backend (`Backend/`, port 8787)

- `src/server.ts`: node:http routes under `/api`; Zod validates every body. Who is calling comes from the signed `x-session` header issued by `POST /api/auth/paypal` (Log in with PayPal, authorization code → userinfo); a member is the trip seat whose `user` is that PayPal id. Friends join with the trip's 6-character code (`POST /api/join`), open until Pricing.
- `src/store.ts`: trip state and every rule-bearing mutation (plan edits keep the trip length via `rebalanceNights`/`fitNights` in `shared/trip.ts`: +1 night at one stop comes from the stop with the most nights; quorum confirms, poll ties, PayPal-only payment status). Splits: a member sets their own share and `rebalanceShares` spreads the rest over the others in proportion, so shares always total 100%; everyone re-accepts, except when a member takes 100%: then only that member has to accept (`readyToCharge` sends the PayPal orders). Store bills can be created with a custom split (`bps`). Entering Pricing auto-prices every stop's winning stay (`priceStays`), and Booked waits for a paid stay per stop. In-store bills (`POST /api/trips/{id}/store-bills`) pay the store's PayPal directly (Orders v2 `payee.email_address`) once everyone on the bill accepts. Persists to `Backend/data.json`.
- `src/wayfinder.ts`: one OpenAI Responses API turn per chat message or event, with a hand-written tool loop (Zod-checked arguments, max 20 steps). Tools are phase-gated per `ai.md` §4; places come from the built-in `web_search` tool. `gpt-5.5` for turns, `gpt-5-mini` for the should-reply check. Before Pricing, Wayfinder edits the plan on request (`update_trip`, `set_stops`, `set_nights` → `store.updateTrip/setStops/setNights`). Needs `OPENAI_API_KEY`. After Places is confirmed, app events (splits, payments, expenses, phase changes) no longer trigger Wayfinder turns (`planning()` in `server.ts`); it still answers members who write in the chat, and still prices a stay it couldn't price.
- `src/integrations.ts`: PayPal Orders v2 + webhook verification, Log in with PayPal + HMAC sessions (`SESSION_SECRET`), Channel3, Kernel, Elasticsearch. Each one is off (HTTP 503 naming the missing variable) until its keys are in `Backend/.env`; see `.env.example`.
- `src/workflows.ts` + `src/tasks.ts`: Render Workflows. With `RENDER_API_KEY` set, the API runs every AI/agent job on the `paytogether-workflows` service (`wayfinder-turn`, `should-reply`, `search-products`, `open-checkout`, `close-checkout`) plus `paypal-orders` and `index-txns`, via `workflows.offload()` (falls back to running in the API if a workflow run fails, so offloaded jobs must be safe to repeat) (`@renderinc/sdk`, task slug `RENDER_WORKFLOW_SLUG/<task>`); without it the same code runs in-process. Trip state stays on the API's disk, so `wayfinder-turn` runs `modelLoop` remotely (product search runs in the workflow itself) and calls back `POST /api/internal/trips/{id}/context|tool` over the private network (`API_HOSTPORT`), authenticated with `ACCESS_TOKEN` only (a session is not enough). Local task server: `render workflows dev -- node src/tasks.ts` (Render CLI ≥ 2.35).
- Opening PayPal first calls `POST /api/trips/{id}/previews/{pid}/pay`, which replaces an order PayPal has expired (bills can wait days) and captures one already approved; store bills load the SDK with `merchant-id=<store email>` so it matches the order's payee. Member colors follow seat position (`PALETTE`, distinct hues first; `recolor` on load and on leave).
- Payment status comes only from PayPal: the verified webhook (`POST /api/paypal/webhook`) or our own server-side capture/order lookup (`applyStatus` in `server.ts`), never the browser. So a payment shows as paid even without a webhook tunnel; approvals and failures still arrive by webhook. The Spending grid lists only paid transactions; a paid share leaves Payments due.
- Solo trips (`solo: true`, created with "Just me") refuse `POST /api/join`. A group trip can't confirm any phase until it has a second member (`confirmBlocker`); the creator waits on `#/setup/{id}`, sharing the join code or inviting an account by PayPal email (`POST /api/trips/{id}/invite`). Invites only find accounts that have logged in before (`store.users`, saved next to the trips file as `*.users.json`); the invitee accepts or declines from home (`GET /api/invites`, `POST /api/trips/{id}/accept|decline`). `GET /api/trips` returns each trip with `mine` (`mySummary` in `shared/trip.ts`) for the home page.
- Frontend and backend deploy separately. `render.yaml` (Render Blueprint) has three services, all built from the repo root because they import `FrontEnd/shared/`: `paytogether-workflows` (see above, region must match the API's), `paytogether-api` (API only; non-`/api` paths 404) on a paid instance with a disk at `/var/data` (`DATA_FILE`), since free instances wipe the filesystem; and `paytogether-web`, a static site from `FrontEnd/web/dist`. The web build bakes in `VITE_API_URL` (the API's URL); the API allows that origin via `WEB_ORIGIN` (CORS). The web site's URL is PayPal's Return URL. `ACCESS_TOKEN` gates every route except `/api/config`, `/api/auth/paypal` and the PayPal webhook; a valid `x-session` also passes, since the hosted page cannot hold the token. The web dev proxy sends the token from `FrontEnd/web/.env` or `.env.local` (`API_URL`, `API_TOKEN`). Vite is pinned to port 5173 (`strictPort`) because the Return URL must match exactly.

## FrontEnd

- `FrontEnd/shared/trip.ts`: plain TS with no imports and no deps. It holds the sample data (mobile), the live trip model and types shared with Backend, the integer-cents split math (largest remainder, basis points summing to 10000), timeline validation, settlement, search and rollups. Keep it import-free so Vite, Metro and `node --test` all load it.
- `FrontEnd/web/`: Vite + React 19 + TS. Tabs: Plan, Spending, Schedule (timeline only; payment blocks link to Spending), Dashboard (`#/trip/{id}/shop` redirects to Spending). Shop sits at the bottom of Spending: Go to split bill (`POST /api/trips/{id}/purchases`) makes an equal split bill (`kind: 'shop'`); once everyone accepts, each pays PayTogether's PayPal. Payments due rows have Pay, Split again (`POST .../previews/{pid}/split-again`, back to Split bills, drops its rows) and Delete (`POST .../previews/{pid}/delete`: toggles a vote, `delete_votes`; everyone on the bill must agree, or only the 100% payer, who deletes at once; removes its Schedule rows); both refused once any share is approved or paid. The Kernel checkout routes are no longer used by the web app; the group chat shows on Plan only and Wayfinder replies pass through `plainText` (paragraphs, no bullet points). The Plan tab covers Destinations → Timeline → Places; confirming Places sends everyone to Spending. The Schedule's Log expense takes the details plus Already paid / Just planned (no split) and opens Spending. Only me (`only_me`) skips splitting: paid goes straight to the transactions, planned straight to Payments due at 100%. Otherwise both become a `plan` bill in Split bills starting equal (`createLoggedBill`). Once everyone accepts, a paid one becomes transactions owed to the logger (`paid_by`, `recordPaidBill`) and a planned one sends PayPal requests (`settleIfReady` in `server.ts`). Each PayPal SDK src loads under its own `data-namespace` global (`loadSdk` in `ui.tsx`). Spending starts with Split bills and Payments due (`Bills.tsx`: AG Grid of accepted shares with a Pay button per row, no store form), then the transactions grid, whose Paid at a store button pays the vendor now (`POST /api/trips/{id}/store-pay`): a PayPal email is the order's payee; a phone number pays PayTogether's account and, once captured, the server sends a PayPal Payout to that phone (`sendPayout`, recorded in `trip.payouts`; Payouts must be enabled on the live account). On capture the bill becomes the entered split as In-store rows (`finishStorePay`) and leaves Payments due; both grids color each member's rows. Members see three trip statuses (`tripStatus` in `shared/trip.ts`): Not planned yet, In progress, Completed. Payments on the Schedule and in home's Recent charges show three stages (`payStage`): Awaiting payment, Verifying (approved in PayPal, waiting for the webhook), Paid. The owner can delete a trip until any PayPal request exists (`DELETE /api/trips/{id}`); joined members can leave (`POST /api/trips/{id}/leave`) before Pricing while the trip has no bills, since members are stored by position; leaving removes their messages, votes and confirmations. Delete also clears the trip's Elasticsearch rows. Grids have no header sorting. Chat renders LaTeX with KaTeX (`RichText` in `ui.tsx`). Hash routes `#/` (landing, signed out; home when signed in), `#/home`, `#/trips`, `#/new`, `#/join`, `#/setup/{id}`, `#/trip/{id}/{plan|schedule|spending|dashboard}`. In dev `vite.config.ts` proxies `/api` to the Backend (`API_URL`, default http://localhost:8787); a deployed build calls `VITE_API_URL` directly. Vite allows `..` for `shared/`. AG Grid 36 (Enterprise row grouping; set `VITE_AG_GRID_LICENSE` in `web/.env.local` to remove the watermark) and AG Charts 14. The trip polls every 2 s.
- `FrontEnd/mobile/`: Expo SDK 58 + React Native 0.88, sample data only. Its Wayfinder replies come from the keyword stand-in `wayfinderReply()` in `shared/trip.ts`; switch it to the Backend API next. Add packages with `npx expo install`.

Commands:
```
cd Backend && npm install && npm run dev        # API on :8787 (reads Backend/.env)
cd Backend && npm test | npm run typecheck      # store rules (single test: npm test -- --test-name-pattern "<name>")
cd FrontEnd && node --test shared/              # money/timeline/search tests
cd FrontEnd/web && npm run dev | npm run build | npm run lint
cd FrontEnd/mobile && npx expo start | npx tsc --noEmit
```
